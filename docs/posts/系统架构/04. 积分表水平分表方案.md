## 1. 背景与目标

### 1.1 现状

当前业务核心表的数据量已经达到了千万级别，过高的数据量已经影响到了当前的业务功能，并且对我们未来的功能规划也产生相应的影响，我们已经对最核心的慢sql做了相应的优化，但由于数据量整体较大，最终的解决方法还是在数据库层面进行调整。
### 1.2 目标

- 单表数据量控制在 1000 万行以内；
- 核心查询接口响应时间恢复正常；
- 迁移过程 **0 停机、0 数据丢失**，业务无感知；
- 保留完整回滚能力，任意阶段可回退。

---

## 2. 方案选型

### 2.1 分区

**调研结论**：阿里云 RDS 8.0 支持分区，但存在以下限制：

- 唯一键（含主键）必须包含分区键，会破坏现有联合唯一索引，导致相关查询变慢；
- 分区后只能 `DROP PARTITION`，数据随之丢失，回滚成本极高；
- 灵活性不足，无法满足后续扩容需求。

**结论**：放弃分区方案。
### 2.2 分库

分库解决的是单库并发瓶颈，当前瓶颈在于单表数据量过大，未达到分库阈值。且分库引入跨库事务、跨库 JOIN、结果集合并等复杂问题，引入复杂度远超收益。

**结论**：放弃分库方案。
### 2.3 水平分表

积分表列数适中，问题是行数过多，水平分表可直接降低单表数据量。使用 **gorm-sharding** 框架实现，无需引入额外中间件。

## 3. 分表设计

### 3.1 Sharding Key 选择

**选择 `user_id` 作为 sharding key**，理由如下：

- 积分的新增、兑换、查询操作均必须关联 `user_id`，天然满足"查询必带 sharding key"的要求；
- 如果使用主键 `id` 作为`sharding key`可能某些逻辑无法正常进行，例如导致判断订单是否重复时尚未生成`id`，所以其无法作为 sharding key；
- `user_id` 分配均匀，hash 后各分表数据分布均衡。

**sharding key 处理**：`user_id` 为 `varchar(55)` 类型，路由时使用 CRC32 处理后取模，保证分布均匀：

```go
// sharding 路由函数
func shardingIndex(userID string, tableCount int) int {
    h := crc32.ChecksumIEEE([]byte(userID))
    return int(h) % tableCount
}
```

### 3.2 分表策略

在选择实际分表数量时，我们同产品同时进行讨论，由于业务后期会全量接入到区块链层，也就意味每日新增的数据大概在15w+，也就是一年是5000w+，按照30个表进行分配，就是每个表大概不到200万，对于我们而言是符合预期的，并且就是在3年内，每个表也不会到达1000万。并且在考虑到后期分表的数据达到瓶颈后该如何处理：

1. 根据实际业务对表数据进行归档，将待归档数据同步至低成本的存储中，然后删除旧表并同步数据至新表；
2. 将表扩充至60个表，这样可以保证迁移的数据只有一半；

### 3.3 新表结构

新积分表在旧表基础上的主要变化：

```sql
CREATE TABLE integral_info_00 (
    id          BIGINT       NOT NULL COMMENT '雪花算法生成，全局唯一',
    user_id     VARCHAR(55)  NOT NULL COMMENT 'sharding key',
    amount      BIGINT       NOT NULL COMMENT '积分数量',
    status      TINYINT      NOT NULL COMMENT '积分状态',
    source      VARCHAR(32)  NOT NULL COMMENT '积分来源',
    created_at  DATETIME     NOT NULL,
    updated_at  DATETIME     NOT NULL,
    PRIMARY KEY (id),
    INDEX idx_user_id (user_id),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
-- integral_info_01 ~ integral_info_31 结构相同
```

## 四、数据迁移方案

整体迁移分为三个阶段，全程不停机。

```
阶段一：冷数据同步          阶段二：双写热数据           阶段三：灰度切流
─────────────────    →    ─────────────────    →    ─────────────────
同步历史存量数据              新写入同时写旧表+新表           按比例逐步切流
对账验证数据一致              异步补偿保障最终一致           最终下线旧表逻辑
```

### 4.1 阶段一：冷数据同步

**目标**：将旧表历史存量数据迁移到新分表，并完成对账验证。

**同步服务设计**：

```go
// 分批读取旧表数据，按 user_id 写入对应分表
func SyncBatch(startID, endID int64) error {
    records := oldDB.Where("id BETWEEN ? AND ?", startID, endID).Find()
    for _, r := range records {
        tableIndex := shardingIndex(r.UserID, 32)
        newDB.Table(fmt.Sprintf("integral_info_%02d", tableIndex)).Create(r)
    }
    // 写入同步进度记录
    saveSyncProgress(startID, endID, "done")
    return nil
}
```

**同步进度表**：

```sql
CREATE TABLE sync_progress (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    start_id   BIGINT      NOT NULL COMMENT '本批次起始ID',
    end_id     BIGINT      NOT NULL COMMENT '本批次结束ID',
    status     VARCHAR(16) NOT NULL COMMENT 'pending/done/failed',
    created_at DATETIME    NOT NULL
);
```

**对账验证（按用户维度）**：

```sql
-- 验证某用户在旧表和新表的数据是否一致
SELECT user_id, COUNT(*) AS cnt, SUM(amount) AS total
FROM integral_info
WHERE user_id = ?

-- 对比新表同用户数据
SELECT user_id, COUNT(*) AS cnt, SUM(amount) AS total
FROM integral_info_xx   -- 根据 sharding 路由确定表号
WHERE user_id = ?
```

对账维度：

- **条数对齐**：旧表 vs 新表同用户记录总数；
- **总额对齐**：旧表 vs 新表同用户积分总额；
- **关键状态抽样**：随机抽取 1% 记录，逐字段比对 `status`、`updated_at` 等状态字段。

对账结果写入对账记录表，全部通过后方可进入阶段二。

---

### 4.2 阶段二：双写热数据

**目标**：新增的热数据同时写入旧表和新表，保持两张表实时一致。

**双写一致性方案**：采用「主写旧表 + 异步补偿写新表」，而非同事务双写。

> 同事务双写在极端情况下（commit 时网络抖动）仍可能出现两边状态不确定的问题，异步补偿 + 对账兜底是更稳妥的方案。

```go
func AddIntegral(ctx context.Context, req *AddIntegralReq) error {
    // 1. 主写旧表（保障主业务）
    if err := oldDB.Create(req.ToOldModel()); err != nil {
        return err
    }

    // 2. 异步写新表（不阻塞主流程）
    go func() {
        if err := writeToNewTable(req); err != nil {
            // 写入补偿队列，等待重试
            compensationQueue.Push(req)
            log.Errorf("write new table failed, pushed to compensation queue: %v", err)
        }
    }()

    return nil
}

// 补偿任务：定时重试写入失败的记录
func CompensationWorker() {
    for item := range compensationQueue.Consume() {
        if err := writeToNewTable(item); err != nil {
            // 超过最大重试次数，告警人工介入
            alert.Send("compensation failed after max retry", item)
        }
    }
}
```

**补偿队列可选方案**：

- 轻量场景：写入 Redis List，定时任务消费；
- 重要场景：写入 Kafka，消费者保障 at-least-once 投递。

---

### 4.3 阶段三：灰度切流

**目标**：逐步将流量从旧表切到新表，出现问题时爆炸半径可控。

**灰度策略**：按 `user_id` 尾号控制流量比例。

|阶段|流量比例|观察时长|回滚条件|
|---|---|---|---|
|Canary|5%（尾号 0、1）|24h|错误率 > 0.1% 立即回滚|
|灰度 20%|20%（尾号 0~3）|48h|同上|
|灰度 50%|50%（尾号 0~4 奇）|72h|同上|
|全量|100%|持续观察|同上|

**代码实现**：

```go
func routeToNewTable(userID string) bool {
    // 取 user_id 最后一位数字判断灰度
    lastChar := userID[len(userID)-1]
    lastDigit := int(lastChar - '0')
    return lastDigit < grayScaleThreshold  // 动态配置，初始为 2
}

func AddIntegral(ctx context.Context, req *AddIntegralReq) error {
    if routeToNewTable(req.UserID) {
        return newTableService.Add(ctx, req)  // 走新表逻辑
    }
    return oldTableService.Add(ctx, req)  // 走旧表逻辑
}
```

`grayScaleThreshold` 通过配置中心动态下发，无需重新部署即可调整灰度比例。

## 五、代码分支规划

|分支|用途|新表|旧表|部署阶段|
|---|---|---|---|---|
|`master`|当前稳定版，兜底回滚用|✗|✓|常驻备用|
|`master-sharding-pre`（msp）|双写阶段，主写旧表|异步写|主写|阶段二|
|`master-sharding-after`（msa）|切流阶段，主写新表|主写|兼容写|阶段三|
|`new-master`|稳定后，删除旧表逻辑|主写|✗|稳定后上线|

## 六、回滚方案

任意阶段出现问题均可回滚，旧表数据在全量切流并稳定前始终保留。

```
阶段一出问题  →  停止同步服务，直接回滚，无影响
阶段二出问题  →  停止双写，重新部署 master 分支
阶段三出问题  →  调整灰度阈值为 0，流量全部回到旧表
全量切流后    →  旧表数据保留 30 天观察期，确认无异常再清理
```

---

## 七、扩容路径

当分表数量达到瓶颈时，从 32 张扩展到 64 张，利用 2 的幂次方特性简化迁移：

```
初始：user_id CRC32 % 32 → integral_info_05

扩容后：user_id CRC32 % 64
  - 原 integral_info_05 的数据，mod 64 后
  - 一半仍落在 integral_info_05（原表，不动）
  - 另一半迁移到新建的 integral_info_37（新表）

→ 每张表只需迁移一半数据，有规律，热更新可行
```

---

## 八、外部依赖处理

当前大屏服务、BaaS 平台均依赖旧积分表查询，处理策略：

- **切流阶段三期间**：旧表持续双写，外部服务查询旧表，无影响；
- **全量切流后**：新增只读视图或查询接口，外部服务按计划迁移，给予 3 个月过渡期；
- **过渡期结束后**：外部服务完成迁移，旧表进入只读归档状态。

## 九、风险与应对

|风险|概率|影响|应对措施|
|---|---|---|---|
|补偿队列积压，新旧表短暂不一致|中|低|监控队列深度，超阈值告警；对账服务每小时全量比对|
|灰度切流期间用户体验不一致|低|低|同一用户路由固定（基于 user_id），不会反复横跳|
|雪花算法时钟回拨导致 ID 重复|低|高|使用成熟的雪花算法库，检测时钟回拨并等待或告警|
|分表后跨表查询缺少 sharding key|中|中|gorm-sharding 框架报 `ErrMissingShardingKey` 强制拦截|
|user_id CRC32 分布不均|低|低|上线前对全量 user_id 做分布统计验证|
